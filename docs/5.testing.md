# Testing

`pnpm test` builds the module and runs `ajs module test .`: the interface-payment and interface-subscriptions conformance suites, and this module's own tests.

## Against the stand-in, or against Mollie

| `MOLLIE_API_KEY` | The suite runs against                                        |
| ---------------- | ------------------------------------------------------------- |
| unset            | a local stand-in for Mollie's API, started by the test config |
| a `test_…` key   | Mollie's test mode at `api.mollie.com`, with no other change  |
| a `live_…` key   | nothing: the suite refuses to run against live payments       |

`MOLLIE_SECOND_API_KEY` (a second test-mode account) enables the multi-account tests against Mollie; the stand-in always has two accounts.

The **stand-in** (`src/test/stand-in`) answers the part of Mollie's API the module uses, as Mollie's OpenAPI specification and documentation describe it. [`SOURCES.md`](../src/test/stand-in/SOURCES.md) lists every behaviour it models and what that rests on: the specification, a documentation page, a response observed from Mollie, another project's tests, or an assumption. A green run against the stand-in shows that the module agrees with that reading of the documentation; the assumptions are what a first run against Mollie checks.

## The test payer

Mollie's test mode settles nothing on its own. A payer-present payment waits on a test-mode checkout page where the tester picks the outcome; an off-session charge waits on its `changePaymentState` page (Mollie: _Testing_). The suites expect charges to settle within 30 seconds, so the test config starts a **test payer** that does what a tester would: it watches recent payments, and for every open `first` or `recurring` payment it opens the page, picks the method if asked, and submits a final state:

- a `first` payment (saving a card): `paid`;
- a charge against a mandate the test marked as declining: `failed`;
- a held charge (`captureMode: manual`): `authorized`;
- any other charge: `paid`.

Hosted one-off payments are left alone: the checkout tests expect them to stay open.

The payer drives the stand-in's pages and Mollie's the same way, by the forms' field names. Mollie's form fields come from another project's tests against Mollie's test mode, not from Mollie's documentation, so the payer is unverified against Mollie until the first live run.

Before the suites load, the test config uses the payer to save two cards through real first payments: one whose charges succeed (`ANTELOPE_PAYMENT_TEST_METHOD`), one whose charges the payer declines (`ANTELOPE_PAYMENT_TEST_METHOD_DECLINED`). The subscriptions suite saves its own cards, with `ANTELOPE_PAYMENT_TEST_METHOD` set to `creditcard`: a Mollie saved method belongs to one customer, while that suite saves a method for each customer it creates.

## What the conformance suites cannot check here

These conformance tests are reported pending by name, with the reason, on every run:

| Test                                                           | Why it cannot pass on Mollie                                                                                                   |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| payment: _saves a method against a customer and lists it back_ | It charges one test token for a brand-new customer. Mollie's saved methods are mandates that belong to one customer.           |
| payment: _authorizes without capturing, then captures in part_ | Mollie creates an off-session payment `open` and authorizes it afterwards; the test reads `authorized` from the creating call. |
| payment: _releases an authorization on cancel_                 | The same.                                                                                                                      |
| payment: _resolves a decline instead of throwing_              | Mollie reports a declined off-session payment after the creating call; the test reads `failed` from it.                        |
| subscriptions: _starts a trial without charging anything_      | Mollie schedules by date; the trial end comes back rounded up to the next Amsterdam midnight, not to the second.               |
| subscriptions: _defers the first charge to a billing anchor_   | The same, for the anchor.                                                                                                      |

and one more only when the coming month crosses a daylight-saving change in Europe/Amsterdam:

| subscriptions: _charges the first period at once and reports it active_ | Its period runs from one Amsterdam midnight to another, an hour off whole days; the test allows at most 31 days of exactly 24 hours. |

The suite's own `a declined first period` tests are skipped as well: they need a card that saves on-session and is declined off-session, and Mollie reports that decline after `CreateSubscription` returns.

Each of these flows is covered by this module's own tests instead, settled the way Mollie settles them: held and then captured, declined after the call, trials rounded to the day.

## What only a live run can show

The live run is what checks the assumptions in [`SOURCES.md`](../src/test/stand-in/SOURCES.md). Beyond those:

- **Webhooks.** A test container cannot receive Mollie's deliveries, so against Mollie the event tests are skipped (`ANTELOPE_SUBSCRIPTIONS_TEST_EVENTS` is set only for the stand-in, which delivers in-process). `VerifyWebhook` itself is exercised by calling it with the deliveries Mollie would send.
- **Subscription renewals.** Mollie fires renewals on their dates and has no test clock, so renewals, retries and cancellation after failed retries are tested against the stand-in only.
- **Timing.** When in the day Mollie charges a subscription date, and in which time zone it reads one.
