`pnpm test` builds the module and runs `ajs module test .`. That runs the interface-payment and interface-subscriptions conformance suites, and this module's own tests.

## Against the stand-in, or against Mollie

| `MOLLIE_API_KEY` | The suite runs against                                          |
| ---------------- | --------------------------------------------------------------- |
| unset            | a local stand-in for Mollie's API, started by the test config   |
| a `test_…` key   | Mollie's test mode at `api.mollie.com`, with no other change    |
| a `live_…` key   | nothing, because the suite refuses to run against live payments |

`MOLLIE_SECOND_API_KEY`, a second test-mode account, enables the multi-account tests against Mollie. The stand-in always has two accounts.

The **stand-in** (`src/test/stand-in`) answers the part of Mollie's API that the module uses, as Mollie's OpenAPI specification and documentation describe it. [`SOURCES.md`](../src/test/stand-in/SOURCES.md) lists every behaviour it models and what that behaviour rests on: the specification, a documentation page, a response observed from Mollie, another project's tests, or an assumption. A green run against the stand-in shows that the module agrees with that reading of the documentation. A first run against Mollie checks the assumptions.

## The test payer

Mollie's test mode settles nothing on its own. A payer-present payment waits on a test-mode checkout page where the tester picks the outcome. An off-session charge waits on its `changePaymentState` page (Mollie: _Testing_). The suites expect a charge to settle within 30 seconds, so the test config starts a **test payer** that does what a tester would. It watches recent payments. For every open `first` or `recurring` payment, it opens the page, picks the method if asked, and submits a final state:

- A `first` payment, which saves a card, gets `paid`.
- A charge against a mandate that the test marked as declining gets `failed`.
- A held charge (`captureMode: manual`) gets `authorized`.
- Any other charge gets `paid`.

The payer leaves hosted one-off payments alone, because the checkout tests expect them to stay open.

The payer drives the stand-in's pages and Mollie's pages the same way, by the forms' field names. Mollie's form field names come from another project's tests against Mollie's test mode, not from Mollie's documentation. So the payer is unverified against Mollie until the first live run.

Before the suites load, the test config uses the payer to save two cards through real first payments. Charges on the first card succeed (`ANTELOPE_PAYMENT_TEST_METHOD`), and the payer declines charges on the second (`ANTELOPE_PAYMENT_TEST_METHOD_DECLINED`). The subscriptions suite saves its own cards, with `ANTELOPE_PAYMENT_TEST_METHOD` set to `creditcard`. A Mollie saved method belongs to one customer, and that suite saves a method for each customer it creates.

## What the conformance suites cannot check here

Every run reports these conformance tests as pending, by name and with the reason:

| Test                                                           | Why it cannot pass on Mollie                                                                                                   |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| payment: _saves a method against a customer and lists it back_ | It charges one test token for a brand-new customer. Mollie's saved methods are mandates that belong to one customer.           |
| payment: _authorizes without capturing, then captures in part_ | Mollie creates an off-session payment `open` and authorizes it afterwards. The test reads `authorized` from the creating call. |
| payment: _releases an authorization on cancel_                 | The same.                                                                                                                      |
| payment: _resolves a decline instead of throwing_              | Mollie reports a declined off-session payment after the creating call. The test reads `failed` from that call.                 |
| subscriptions: _starts a trial without charging anything_      | Mollie schedules by date. The trial end comes back rounded up to the next Amsterdam midnight, not to the second.               |
| subscriptions: _defers the first charge to a billing anchor_   | The same, for the anchor.                                                                                                      |

One more test is pending only when the coming month crosses a daylight-saving change in Europe/Amsterdam:

| Test                                                                    | Why it cannot pass on Mollie                                                                                                         |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| subscriptions: _charges the first period at once and reports it active_ | Its period runs from one Amsterdam midnight to another, an hour off whole days. The test allows at most 31 days of exactly 24 hours. |

The suite skips its own `a declined first period` tests as well. They need a card that saves on-session and is declined off-session, and Mollie reports that decline after `CreateSubscription` returns.

This module's own tests cover each of these flows instead, settled the way Mollie settles them: held and then captured, declined after the call, and trials rounded to the day.

## What only a live run can show

The live run checks the assumptions in [`SOURCES.md`](../src/test/stand-in/SOURCES.md). It also shows the following:

- **Webhooks.** A test container cannot receive Mollie's deliveries, so against Mollie the event tests are skipped. The test config sets `ANTELOPE_SUBSCRIPTIONS_TEST_EVENTS` only for the stand-in, which delivers in-process. The tests call `VerifyWebhook` directly with the deliveries Mollie would send.
- **Subscription renewals.** Mollie fires renewals on their dates and has no test clock. So only the stand-in tests renewals, retries, and cancellation after failed retries.
- **Timing.** A live run shows when in the day Mollie charges on a subscription date, and in which time zone Mollie reads that date.
