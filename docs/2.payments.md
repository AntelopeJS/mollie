## Statuses

Mollie has seven payment statuses. The interface has six.

| Mollie                       | Interface         | Why                                                                                    |
| ---------------------------- | ----------------- | -------------------------------------------------------------------------------------- |
| `open`, with a checkout link | `requires_action` | The payer must go to the link, which is the payment's `redirectUrl`                    |
| `open`, without one          | `pending`         | An off-session charge that Mollie has not settled yet                                  |
| `pending`                    | `pending`         | Awaiting the bank                                                                      |
| `authorized`                 | `authorized`      | Funds held, awaiting capture                                                           |
| `paid`                       | `succeeded`       |                                                                                        |
| `failed`                     | `failed`          | `failure` comes from Mollie's `failureReason` (cards) or `bankReasonCode` (SEPA)       |
| `canceled`                   | `canceled`        |                                                                                        |
| `expired`                    | `canceled`        | In Mollie's terms, the payer abandoned it, or nobody captured an authorization in time |

The module normalises `failure.code` from Mollie's reasons:

| Mollie reason                                                                                                    | `failure.code`          |
| ---------------------------------------------------------------------------------------------------------------- | ----------------------- |
| `insufficient_funds`, SEPA `AM04`                                                                                | `insufficient_funds`    |
| `card_expired`                                                                                                   | `expired_card`          |
| `invalid_card_holder_name`, `invalid_card_number`, `invalid_cvv`, SEPA `AC01`                                    | `incorrect_details`     |
| `authentication_abandoned`, `authentication_failed`, `authentication_required`, `authentication_unavailable_acs` | `authentication_failed` |
| Any other reason, `invalid_card_type` included                                                                   | `declined`              |

`failure.providerCode` holds the reason verbatim.

## Amounts

Mollie takes an amount as a string with the currency's decimals. Mollie uses two decimals for every currency it lists, and none for `ISK` and `JPY` (Mollie: _Multicurrency_). The module converts from the interface's minor units with Mollie's table, not with the runtime's currency data, because the two disagree for some currencies that Mollie supports. Node's ICU data gives `HUF` no decimals and Mollie gives it two, so `{ value: 1050, currency: "HUF" }` is `"10.50"`. For a currency that Mollie does not list, the module falls back to the runtime's currency data (`Intl.NumberFormat`).

## What `paymentMethod` may be

| Value              | Meaning                                                              | Mollie request                                   |
| ------------------ | -------------------------------------------------------------------- | ------------------------------------------------ |
| `cst_…:mdt_…`      | A saved method, from `ListPaymentMethods`                            | `sequenceType: recurring`, the mandate           |
| `tkn_…`            | A card token from Mollie Components, collected by your own card form | `method: creditcard`, `cardToken`                |
| a Mollie method id | The method your own picker chose: `ideal`, `creditcard`, `paypal`, … | `method`, and the payer skips Mollie's selection |
| absent             | Mollie's hosted page lets the payer choose                           | no `method`                                      |

Any other value rejects with `CustomerNotFoundError` for the payment method.

The module charges a saved method as a Mollie recurring payment, which needs no payer, whether or not `offSession` is set. A saved method belongs to one customer. Charging it for another customer rejects with `CustomerNotFoundError` for the method. `offSession` needs a saved method, and `offSession` combined with `savePaymentMethod` rejects with `PaymentError`.

## Payer-present payments are redirects

Mollie has no payment that completes inside the creating call while the payer is present. `CreatePayment` without a saved method, and `CreateCheckoutSession`, both return `requires_action` with Mollie's checkout URL. So `CreatePayment` requires `returnUrl` unless it charges a saved method.

`savePaymentMethod` needs a `customer`. It makes the payment a Mollie `first` payment. Once the payer completes it, Mollie creates a mandate for the customer, and `ListPaymentMethods` lists it. `ListPaymentMethods` lists a Mollie mandate when the mandate is `valid` and usable without the payer (scope `customer-not-present`). It does not list a card saved for one-click checkout only, because that card cannot be charged off-session.

## The hosted page language

`CreateCheckoutSession` turns its `locale` into Mollie's `locale`, which sets the language of Mollie's hosted page (Mollie: _Create payment_, `locale`). Mollie names a language with its region, such as `en_GB` or `fr_FR`, and accepts only the locales it lists. The module picks one in three steps:

1. A locale Mollie accepts as it is goes with `-` replaced by `_`. Of the interface's values, only `en-GB` does, and becomes `en_GB`.
2. A bare language, or a regional one Mollie does not offer, gets the region Mollie offers that language in. So `fr` is `fr_FR`, `en` is `en_US`, and `pt-BR` is `pt_PT`.
3. A language Mollie does not offer, and `auto`, send no locale. Mollie then picks the language from the payer's browser.

## Off-session charges settle later

Mollie creates a charge against a saved method `open` and settles it afterwards, so `CreatePayment` returns `pending`. The outcome arrives as a `payment.succeeded`, `payment.authorized` or `payment.failed` event, or through `GetPayment`. A decline is a `failed` payment that Mollie reports after the call returns. The interface's rule that a decline is a result, not an exception, still holds, but the result is not in the creating call.

## Holding funds with `authorizeOnly`

Mollie can hold funds for later capture only for cards, Klarna, Billie, Riverty, Vipps, MobilePay, PayPal and Billink (Mollie: _Place a hold for a payment_). On a hosted page, Mollie charges at once a payer who picks any other method. So the module does the following:

- With a saved method, it reads the mandate's method first and refuses a SEPA Direct Debit mandate with a `PaymentError`.
- With a Mollie method id, it refuses any method outside that list with a `PaymentError`.
- On a hosted page, it offers the payer only those methods.

When the module refuses a request, nothing reaches Mollie. A hold on a saved method reads `pending` until Mollie reports it `authorized`. A hold on a hosted page reads `requires_action` while it waits on the payer. `CapturePayment` captures once. Capturing less than the held amount releases the rest, as Mollie does for cards. `CancelPayment` on an authorized payment releases it. Mollie processes a release asynchronously, so the payment may still read `authorized` for a moment.

## Refunds

Mollie requires an amount, so a refund without one refunds what Mollie reports as remaining. Mollie has no refund reason. The module keeps the reason and the idempotency key in the refund's metadata, outside what `Refund.metadata` returns, and also writes the reason into the refund's description. Refund statuses map as follows:

- `queued`, `pending` and `processing` are `pending`.
- `refunded` is `succeeded`.
- `failed` and `canceled` are `failed`.

## Cancelling

The module cancels an `open` or `pending` payment with Mollie's cancel endpoint while Mollie says it can (`isCancelable`). The module returns a payment that is already `canceled` or `expired` as it is, so a repeated cancellation is harmless. Any other payment rejects with `InvalidPaymentStateError`.

## Errors

- **Not found.** The module reports Mollie's 404, and an identifier of the wrong shape, as not found.
- **State errors.** `InvalidPaymentStateError` comes only from the module's own reading of the payment before it calls Mollie. Examples are capturing what is not authorized, refunding what is not paid or more than remains, and cancelling what has settled. The module never reads a refusal from Mollie as a state error. Mollie answers 422 for a request it will not process, and, per its documentation, also when the account's payment services are suspended. A 422 is a `PaymentError`, so the module never reports an account problem as "this payment cannot be refunded".
- **Everything else.** A 401, a 429, a 5xx or a network failure is a `PaymentError`. Its `providerCode` carries the HTTP status, and the field Mollie names when there is one.

## Idempotency

Mollie honours `Idempotency-Key` on every POST for **one hour**, and answers 400 when a caller reuses a key with other parameters (Mollie: _API idempotency_).

- `RefundPayment` and `CapturePayment` replay at any time. A key reused with other parameters returns the earlier result instead of Mollie's 400. The module stores the key in the refund's or capture's own metadata, and each call first looks among the payment's refunds or captures for one made under that key. A replay returns the original refund, or the payment as captured. That holds even after the payment's state no longer allows the operation, and even after Mollie has forgotten the key. A partial refund replayed after the hour does not refund twice.
- `CreatePayment`, `CreateCheckoutSession`, `CreateCustomer` and a release replay within the hour, through Mollie's own key handling. After the hour, Mollie treats the key as new. That is Mollie's limit, and the module does not widen it for these calls.
- `CreateSubscription` replays at any time (see [Subscriptions](./4.subscriptions.md)).

Mollie ignores the key on DELETE. Cancelling a payment, deleting a customer and detaching a method are DELETEs. A repeated cancellation returns the cancelled payment, while a repeated deletion or detachment reports the record as not found.
