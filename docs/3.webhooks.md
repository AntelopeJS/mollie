# Webhooks

## What Mollie sends

For payments, Mollie uses "classic" webhooks: the `webhookUrl` given when the payment (or the subscription that created it) was made is called with a form-encoded body of one field, `id=tr_…`, and nothing else. The delivery is not signed. Mollie's own guidance is to read the payment back and act on what the API says, never on the request (Mollie: _Webhooks_).

The same URL is called when the payment changes status, when one of its refunds reaches `processing`, `refunded` or `failed`, and when a chargeback is received. Every one of those deliveries carries the payment's id.

## How `VerifyWebhook` establishes a delivery

1. The body is read as a form and only `id` is taken. A body without a `tr_…` id is rejected with `WebhookVerificationError`.
2. The payment is read back from Mollie with the account's key (the `provider` selector chooses the account). If Mollie has no such payment on the account, the delivery is rejected with `WebhookVerificationError`.
3. If Mollie cannot be reached, or answers with any other error, the call rejects with a plain `PaymentError`: your route answers with a server error and Mollie delivers again, rather than a 403 that reads an outage as a forgery.

**Every field of the event comes from the payment read back**: the type, the payment, its status, amounts and metadata. The body is a pointer and nothing else. A body that also claims `status=paid` changes nothing, and a forged delivery naming a real payment yields that payment's real state. This is the interface's rule for providers verified by re-fetching rather than by signature.

## Which events

| Payment status at Mollie | Event                | Event id                  |
| ------------------------ | -------------------- | ------------------------- |
| `pending`                | `payment.pending`    | `<payment id>:pending`    |
| `authorized`             | `payment.authorized` | `<payment id>:authorized` |
| `paid`                   | `payment.succeeded`  | `<payment id>:paid`       |
| `failed`                 | `payment.failed`     | `<payment id>:failed`     |
| `canceled`               | `payment.canceled`   | `<payment id>:canceled`   |
| `expired`                | `payment.canceled`   | `<payment id>:expired`    |
| `open`                   | none (`undefined`)   |                           |

The event id is derived from the payment and its status, so every delivery of one state carries the same id, and de-duplicating on it is enough. `createdAt` is when Mollie recorded that status (`paidAt`, `failedAt`, …).

A payment made for a subscription carries `antelopeSubscription` in its metadata, and its delivery also raises the subscription's `payment_succeeded` or `payment_failed` (see [Subscriptions](./4.subscriptions.md)). If a subscription handler throws, `VerifyWebhook` rejects, and Mollie delivers again.

## What is not raised, and why

**`refund.succeeded`, `refund.failed` and `dispute.opened` are never raised.** A classic delivery for a refund or a chargeback names the payment, not the refund or the chargeback, and nothing in it says which of the payment's changes caused it. `VerifyWebhook` returns one event per delivery. Picking a refund out of the payment read back would be a guess: one delivery can follow a refund settling, a chargeback arriving, or the payment's own status changing, and a wrong guess swallows the payment's own event. The delivery that follows a refund is therefore reported as the payment's own state, under the same id as before, and de-duplicates away.

Read a refund's outcome with `GetRefund`, and a payment's refunded total with `GetPayment`.

### Why not Mollie's next-gen webhooks

Mollie also has signed "next-gen" webhooks (`X-Mollie-Signature`, an HMAC-SHA256 of the body), with event types for refunds and chargebacks. They do not fit here today (Mollie: _Next-gen webhooks_):

- Mollie itself recommends classic webhooks for payment updates.
- Creating one through the API needs an advanced access token or OAuth; this module uses API keys only. Created in the dashboard instead, they deliver a _simple_ payload — ids and type, without the record — and a refund cannot be read without its payment's id.
- The refund and chargeback event types are in beta, and Mollie does not document whether next-gen events cover subscription payments.

When those change, signed deliveries for refunds and chargebacks are the way to raise `refund.*` and `dispute.opened`.

## Testing a webhook route

Mollie refuses a `localhost` webhook URL. In test mode, deliveries still happen, to a public URL; a tunnel (ngrok or similar) is the usual way to receive them locally.
