## What Mollie sends to your route

For payments, Mollie uses "classic" webhooks. Mollie calls the `webhookUrl` that the module gave when it made the payment, or the subscription that created the payment. The body is form-encoded with one field, `id=tr_…`, and nothing else. Mollie does not sign the delivery. Mollie's own guidance is to read the payment back and act on what the API says, never on the request (Mollie: _Webhooks_).

Mollie calls the same URL when the payment changes status, when one of its refunds reaches `processing`, `refunded` or `failed`, and when Mollie receives a chargeback. Every one of those deliveries carries the payment's id.

## How `VerifyWebhook` establishes a delivery

1. `VerifyWebhook` reads the body as a form and takes only `id`. A body without a `tr_…` id rejects with `WebhookVerificationError`.
2. `VerifyWebhook` reads the payment back from Mollie with the account's key. The `provider` argument chooses the account. If Mollie has no such payment on the account, the delivery rejects with `WebhookVerificationError`.
3. If Mollie cannot be reached, or answers with any other error, the call rejects with a plain `PaymentError`. Your route then answers with a server error and Mollie delivers again. A 403 would read an outage as a forgery.

**Every field of the event comes from the payment read back.** That covers the type, the payment, its status, its amounts and its metadata. The body only points at a payment. A body that also claims `status=paid` changes nothing, and a forged delivery that names a real payment yields that payment's real state. The payment interface sets this rule for providers that verify by reading the record back instead of by signature.

## Which events

| Payment status at Mollie | Event                | Event id                  |
| ------------------------ | -------------------- | ------------------------- |
| `pending`                | `payment.pending`    | `<payment id>:pending`    |
| `authorized`             | `payment.authorized` | `<payment id>:authorized` |
| `paid`                   | `payment.succeeded`  | `<payment id>:paid`       |
| `failed`                 | `payment.failed`     | `<payment id>:failed`     |
| `canceled`               | `payment.canceled`   | `<payment id>:canceled`   |
| `expired`                | `payment.canceled`   | `<payment id>:expired`    |
| `open`                   | none (`undefined`)   |                           |

The module derives the event id from the payment and its status, so every delivery of one state carries the same id, and de-duplicating on the id is enough. `createdAt` is when Mollie recorded that status, from `authorizedAt`, `paidAt`, `failedAt`, `canceledAt` or `expiredAt`. For `pending`, it is when Mollie created the payment.

A payment made for a subscription is either the first period, whose metadata names the subscription under `antelope.subscription`, or a renewal, which Mollie links to the subscription with `subscriptionId`. Its delivery also raises the subscription's `payment_succeeded` or `payment_failed` event (see [Subscriptions](./4.subscriptions.md)). If a subscription handler throws, `VerifyWebhook` rejects, and Mollie delivers again.

## What is not raised, and why

**The module never raises `refund.succeeded`, `refund.failed` or `dispute.opened`.** A classic delivery for a refund or a chargeback names the payment, not the refund or the chargeback, and nothing in it says which of the payment's changes caused it. `VerifyWebhook` returns one event per delivery. Picking a refund out of the payment read back would be a guess. One delivery can follow a refund settling, a chargeback arriving, or the payment's own status changing, and a wrong guess swallows the payment's own event. So the module reports the delivery that follows a refund as the payment's own state, under the same id as before, and de-duplication drops it.

Read a refund's outcome with `GetRefund`, and a payment's refunded total with `GetPayment`.

### Why not Mollie's next-gen webhooks

Mollie also has signed "next-gen" webhooks (`X-Mollie-Signature`, an HMAC-SHA256 of the body), with event types for refunds and chargebacks. They do not fit this module today (Mollie: _Next-gen webhooks_):

- Mollie itself recommends classic webhooks for payment updates.
- Creating a next-gen webhook through the API needs an advanced access token or OAuth, and this module uses API keys only. A next-gen webhook created in the dashboard delivers a _simple_ payload, with ids and a type but without the record. A refund cannot be read without its payment's id.
- Mollie marks the refund and chargeback event types as beta, and does not document whether next-gen events cover subscription payments.

When those facts change, signed deliveries for refunds and chargebacks are the way to raise `refund.*` and `dispute.opened`.

## Testing a webhook route

Mollie refuses a `localhost` webhook URL. In test mode, Mollie still delivers, to a public URL. To receive deliveries on your machine, expose your route through a tunnel such as ngrok.
